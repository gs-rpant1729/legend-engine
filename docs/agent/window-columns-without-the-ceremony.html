Window Columns Without the Ceremony

legend-engine · implementation plan

Window columns without the ceremony

Extend #5091's group-scoped aggregate pattern to windows, so a window column is written the same way a groupBy column already is — ~run : f | $f->plus(~id) — and add nullary sugar for the ranking and navigation functions. Removes {p,w,r|...} from the ~80% of window columns that never touch p or w, and gives groupBy and windowed extend one shared reducer vocabulary.

1The problem

Every column added inside a windowed extend takes a three-parameter lambda — {p,w,r|...} — whether or not the computation needs a partition or a window spec. A grep of every non-reduce window lambda in the current PCT suite:

Body patternCountUses
$r.i / $r.id / $r.name / $r.grp / $r.menu_cogs_usd93only r — p and w declared and ignored
$p->lead($r)..., $p->lag($r)..., $p->rowNumber($r)10p and r; w ignored
$p->rank($w,$r), denseRank, percentRank, cumulativeDistribution, first, last, nth14genuinely all three

The parameters are not arbitrary — the native signatures explain the split exactly:

Function familySignatureNeeds w?Why
lead, lag, offset, rowNumber, ntile(Relation<T>, T[, n])NoIndex arithmetic on the already-sorted partition.
rank, denseRank, percentRank, cumulativeDistribution(Relation<T>, _Window<T>, T)YesTie detection needs w.sortInfo to know which columns to re-compare.
first, last, nth(Relation<T>, _Window<T>, T)YesFrame-relative; needs w.frame's boundary.
This is a leak, not a design feature
p (the pre-sorted, materialized partition) and w (the window spec) are artifacts of the evaluator's per-partition loop, not part of the declarative meaning of "sum this column over this window." SQL's RANK() OVER w never asks the caller for a partition or a row; TDS 1.0's func(colName, aggregateFn) builder already avoided this.

2Design

Two additive changes, neither requiring a parser change:

  • S1 — frame-scoped aggregates. A new extend overload binds the lambda parameter to the frame as a Relation, exactly as #5091's groupBy overload binds the group. The reducer vocabulary is then shared between the two.
  • S2 — nullary window functions. rank(), lag(~col), sum(~col) become reserved forms the compiler lowers before any backend sees them.
The symmetry this rests on
#5091 already ships groupBy(r, cols, FuncColSpec<{Relation<T>[1]->Any[0..1]}, R>) — one lambda over the whole group. S1 is the same spec type with a window in place of the grouping columns. Because the spec shape is identical, the reducers written for one work unchanged in the other: joinStrings(rel, ~col, sep) already exists and becomes available under a window for free.
Pushdown contract
Relational stores never execute these lambda bodies. Per #5091's doc comment on reduce: they "intercept reduce by function id, so every aggregate written on top of it is pushed down without needing its own processor." A body built from the reducer vocabulary pushes down; a body containing arbitrary code runs in-memory and must fail with a clear routing error on relational. This is the contract groupBy's g|... form already ships with — inherited, not invented.
The one hard correctness requirement
The lambda parameter must be bound to the frame, not the partition. With rows(unbounded(), 0) the two differ on every row but the last, and binding the partition would turn a running total into a constant — while still looking like SQL's SUM(x) OVER w. The natives must reuse the frame-slicing already inside the 5-argument window reduce native rather than reimplementing it, and §6's equivalence tests are the gate.

3.1 The overload

Pure · new signatures, mirroring the groupBy pair
native function extend<T,R>(r:Relation<T>[1], w:_Window<T>[1],
    f:FuncColSpec<{Relation<T>[1]->Any[0..1]}, R>[1]):Relation<T+R>[1];

native function extend<T,R>(r:Relation<T>[1], w:_Window<T>[1],
    f:FuncColSpecArray<{Relation<T>[1]->Any[*]}, R>[1]):Relation<T+R>[1];

Identical spec type to #5091's groupBy overloads, with _Window<T> replacing ColSpec/ColSpecArray. The single-parameter colspec lambda types correctly as of legend-pure ≥5.94.1 — the fix #5091 forced through for its own g|... form.

3.2 The shared reducer vocabulary

Each is a one-line Pure body over the existing 2-argument reduce(rel, map, agg), following aggregation/joinStrings.pure exactly. They take a Relation, so they serve both groupBy and windowed extend:

Pure · new reducers, no natives
function plus<T>(rel:Relation<T>[1], col:ColSpec<(?:Number)⊆T>[1]):Number[1]
{
  $rel->reduce(x|eval($col,$x), y|$y->plus());
}
// max, min, average, stdDev, variance: same shape, different reduce lambda

function count<T>(rel:Relation<T>[1]):Integer[1]
{
  $rel->reduce(x|1, y|$y->plus());   // COUNT(*) — no column to map from
}

// joinStrings(rel, ~col, sep) already exists from #5091 — now works under a window too

4S2 — nullary window functions

S1 removes p and w but keeps a lambda. S2 removes the lambda for the closed set of functions SQL itself writes bare after OVER:

Pure · with S1 only
$t->extend(over(~grp, ~o->ascending()), ~[
  rk      : {p,w,r| $p->rank($w, $r)},
  prevQty : {p,w,r| $p->lag($r).qty},
  total   : f | $f->plus(~qty)])
Pure · with S2
$t->extend(over(~grp, ~o->ascending()), ~[
  rk      : rank(),
  prevQty : lag(~qty),
  total   : sum(~qty)])

4.1 Mechanism

A compile-time lowering, not a reimplementation. The same normalization stage that already handles functionType.NormalizeRequiredFunction for ascending/over/rows/_range recognizes a bare call to one of the reserved names in a windowed extend ColSpec and rewrites it before the graph reaches any backend:

Pure · lowering
~rk : rank()          ⟶  ~rk : {p,w,r| $p->rank($w, $r)}     // existing 3-param native
~prevQty : lag(~qty)  ⟶  ~prevQty : {p,w,r| $p->lag($r).qty} // existing 3-param native
~total : sum(~qty)    ⟶  ~total : f | $f->plus(~qty)          // S1 form + §3.2 reducer

Both lowering targets are code that already ships once S1 lands. No interpreted native, compiled codegen path, or SQL generator observes the difference between sugared and unsugared spellings. The {p,w,r|...} form remains available as the escape hatch for genuinely custom per-row computations.

sum/avg/min/max are exposed as SQL-familiar aliases over §3.2's reducers (whose Pure-level names — plus, average — follow the platform's existing collection vocabulary).

5E3 — frame builders

Independent and cheap. rows/_range are already <<NormalizeRequiredFunction>> library sugar over the Rows/_Range classes, so this is new names only:

Pure · library sugar, no natives
rowsBetween(unboundedPreceding(), currentRow())   // vs. rows(unbounded(), 0)
rangeBetween(preceding(1), following(1))          // vs. _range(-1, 1)

Retires the _range spelling and the bare-0/negative-integer convention from user-facing code.

6PCT coverage

  • Frame-scope equivalence (the §2 gate): each reducer written both ways — frame-scoped and 3-parameter map/reduce — asserted identical, across rows(unbounded(), 0), explicit bounded frames, and the no-explicit-frame default. A test that would pass if the lambda were bound to the partition instead of the frame is not sufficient; running totals must be asserted row by row.
  • Shared-vocabulary tests: each §3.2 reducer used under groupBy and under a window in the same suite, confirming one implementation serves both.
  • S2 lowering: sugared vs. unsugared spelling per reserved function; a composition test mixing sugared ranking, sugared aggregates, and hand-written {p,w,r|...} in one extend.
  • Negative: rank() outside a windowed extend; a non-interceptable lambda body failing with the §2 routing error on relational while succeeding in-memory.

7Sequencing and risks

PRScopeGate
PR 1S1 §3 — overloads, shared reducers, natives, relational dispatchFrame-scope equivalence PCT green on H2/DuckDB/Java binding; cloud stores via pct-cloud-test
PR 2S2 §4 — reserved signatures, lowering, negative compile testsLowering-equivalence PCT on the default profile; no new exclusions expected
PR 3E3 §5 — frame builders; no dependency on PR 1/2, can ship firstLibrary-only PCT
  • Frame vs. partition binding — the §2 correctness requirement. Mitigated by factoring the existing window reduce native's slicing rather than writing new slicing, and gated by §6's equivalence tests.
  • In-memory cost — materializing a frame per row is O(rows × frame size). That is already the cost profile of the existing window reduce path, so no regression, but worth confirming no accidental re-slicing per reducer when a FuncColSpecArray carries several columns over one window.
  • Non-interceptable bodies — must fail with a clear routing error on relational, not silently produce wrong SQL. Same contract as groupBy's g|... today; the error message should name the interceptable vocabulary.
  • No protocol impact — function additions plus a compiler-internal rewrite; nothing is serialized as a protocol class, so Studio/DataCube and versioned protocol packages are untouched.
